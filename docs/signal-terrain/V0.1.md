## Product purpose

SignalTerrain combines terrain/access intelligence with SOTA and eventually radio intelligence to help answer:

**Which summit should I activate, how do I get there, and what do I need once I arrive?**

Initial focus is SOTA activation planning.

This is not a clone of SOTA Goat. This is not a clone of AllTrails. This is not a generic cyber, signals, infrastructure, or knowledge-graph product. Do not restore retired SignalTerrain Cyber copy such as “Understand the world's signals.”

**SOTA Goat** answers “Where are the SOTA summits?”  
**AllTrails** answers “How do I hike this trail?”

V0.1 only begins the first part: discover summits around a loaded region, select one, and inspect retrieved SOTA facts plus honest planning placeholders.

## Architecture

```
Raw SOTA source (api2.sota.org.uk or labeled fixture)
        ↓
SOTA data provider  (ss-sota-provider.js → SignalTerrainSotaProvider)
        ↓
Normalized SignalTerrain SOTA model  (ss-summit-model.js → SignalTerrainSotaModel)
        ↓
Map / search / Summit Detail  (ss-map-app.js → SignalTerrainSotaMapApp)
```

Planning (separate boundary):

```
Future OSM / public-land / routing / DEM providers
        ↓
ss-planning-provider.js → SignalTerrainSotaPlanning
        ↓
Summit Detail Planning section
```

V0.1 planning always returns `status: "not-integrated"` with `value: null`. The UI labels this **Not yet integrated**. It must never show invented trailheads, parking, distances, gain, or times.

Activation zone: `ss-map-app.js` creates an empty Leaflet layer group `activationZoneLayer`. A later release may add a polygon there after a documented, accurate elevation-model calculation. SOTA’s activation zone is typically within about **25 m vertically** of the summit. V0.1 does not approximate that contour.

Leaflet is vendored at `apps/summit-signal/vendor/leaflet/`. SignalTerrain does **not** import Shed Hunting JS, CSS, storage keys, or tile-provider modules. It does **not** import `design-system/signalterrain/**` or `wds-signalterrain-*`. Esri public tile URLs are used independently.

Internal JS globals use the `SignalTerrainSota*` prefix so they cannot be confused with retired cyber identifiers (`wds-signalterrain-*`, knowledge-domain `signalterrain`). File paths, CSS classes (`ss-*`), and DOM ids (`ss-*`) stay on the `/apps/summit-signal/` tree to avoid a destructive rename of a working map.

## Data source actually used in V0.1

| Item | Value |
|------|--------|
| Provider | Summits on the Air (SOTA) public API |
| Host | `https://api2.sota.org.uk` (also advertised as `api-db2.sota.org.uk`) |
| Endpoint | `GET /api/regions/W2/GC` |
| Region | W2 / GC — Greater Catskills (USA — NJ / NY) |
| Retrieved | 2026-09-04 |
| Records | 118 real summit objects |
| Fixture | `apps/summit-signal/data/ss-summits-w2-gc.json` |
| Runtime default | Load the fixture (reliable in local/dev and when CORS blocks live calls) |
| Optional live | `?live=1` fetches the same endpoint and falls back to the fixture on failure |

This is a **labeled development fixture of real retrieved records**, not invented sample peaks. Replace or expand the fixture later without changing the normalized model.

### Fields retrieved (region summit objects)

`summitCode`, `name`, `associationCode`, `associationName`, `regionCode`, `regionName`, `validFrom`, `validTo`, `valid`, `longitude`, `latitude`, `points`, `altM`, `altFt`, `activationCount`, `activationDate`, `activationCall`, `locator`, plus optional `restrictionMask` / `restrictionList` / `notes` stored in the fixture for later use.

Region envelope: `minLat`, `maxLat`, `minLong`, `maxLong` (normalized to `minLng` / `maxLng`).

### Normalization

- Drop records without valid WGS84 coordinates.
- Map to `{ id, name, reference, points, elevationM, elevationFt, lat, lng, maidenhead, maidenheadSource, activationCount, lastActivationDate, lastActivationCall, association*, region*, valid, seasonalBonus, sourceUrl, retrievedAt, visual }`.
- `activationCount` of `0` is a known zero. Missing counts stay **Unavailable**.
- Seasonal bonus is **Unavailable** unless the payload includes a numeric bonus. W2/GC region objects in this retrieval did not include `bonusPoints`.
- Maidenhead prefers SOTA `locator`. If missing, a 6-character square is derived from lat/lng and labeled `(derived)`.
- `visual.*` encodings (difficulty, activation status, weather, accessibility, recommendation) are reserved and unset.

### Caching

- In-memory for the page session.
- `sessionStorage` key `signalterrain-sota-catalog-v0` so a refresh does not refetch the fixture during the same tab session.
- No durable personal cache of SOTA data beyond the session. Do not harvest Esri tiles for offline packs in V0.1.

### Known data limitations

- One SOTA region only (W2/GC). The map is still useful without GPS by fitting that region.
- Browser live fetch may fail (CORS / network). Fixture fallback is honest and labeled.
- Single-summit API (`/api/summits/{assoc}/{code}`) is not used in V0.1; region list supplies activation counts for this dataset.
- Seasonal / winter bonus is not in this region payload — the UI does not invent it.
- Last activation is whatever the region list returned (`activationDate`, `activationCall`).
- No access-restriction UI yet even when `restrictionList` is present in the fixture.

## Free / paid product principle (documentation only)

Do **not** implement billing in V0.1.

Core SOTA/community information should remain useful for free. SignalTerrain should not take community-provided SOTA information and lock it behind a subscription.

If monetization is added later, paid value should come from SignalTerrain-created functionality (advanced planning, offline maps, terrain/weather/propagation intelligence, multi-summit planning, routing, and other computational or convenience features) — not from hiding the SOTA catalogue. Any paid product that still uses the SOTA API still needs SOTA’s commercial permission as required by their terms.

## Future roadmap

### V0.2 (recommended)

First major differentiator: trails + trailheads + parking from legitimate open data.

- OSM-derived trail / trailhead / parking candidates with provenance
- Incomplete OSM must display as incomplete, not as “no trail exists”
- Licensed or open routing for distance, gain, and estimated time — later, with honest uncertainty; V0.2 must not invent hike stats
- Topo contour or DEM-backed **activation-zone overlay** only if the contour is calculated correctly (may wait until after V0.2)
- Additional SOTA regions (still via the provider, not UI-scattered fetches)
- Live API as default when CORS/proxy is solved without fabricating a backend
- ODbL attribution for OSM-derived layers

### Later

Weather, road/access conditions, offline maps, GPS hike tracking, SOTA spots/alerts, activation logging, propagation, GPX import/export, multi-summit trips, intelligent ranking (“which summit should I activate today?”) using driving/hiking distance, gain, difficulty, points, parking, weather, daylight, history, and propagation.

Do not implement that recommendation engine in V0.1.
