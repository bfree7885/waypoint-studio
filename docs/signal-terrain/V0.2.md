# SignalTerrain V0.2

**Status:** In development · unpublished · `noindex`  
**App route:** `/apps/summit-signal/` (do not occupy `/apps/signalterrain/`)  
**This release:** Open access layer — candidate OSM trails, trailheads, and parking around a selected SOTA summit

> **SignalTerrain (SOTA/outdoor, unpublished) is a new product definition and is not the retired SignalTerrain Cyber product.**

> **Mapped trail, trailhead, and parking features are candidate access information derived from OpenStreetMap and may be incomplete or outdated. Verify current access conditions before travel.**

> **SignalTerrain is an independent application and is not affiliated with or endorsed by Summits on the Air (SOTA).**

V0.1 remains the SOTA map/search/detail foundation. V0.2 adds the first differentiator: **how do I physically get onto this mountain?** using legitimate OpenStreetMap data. It is **not** a route planner.

---

## Scope

Included:

- Bounded OSM/Overpass query (or labeled fixture) around the **selected** summit
- Normalized `TrailFeature`, `TrailheadFeature`, `ParkingFeature` with provenance
- Independently toggleable map layers: Summits · Trails · Trailheads · Parking
- Summit Detail **Access** section: nearby mapped paths, trailheads, parking
- Honest states: unavailable vs empty vs found
- Straight-line distance to trailheads and parking, labeled as straight-line
- OSM / ODbL attribution
- Core SOTA map still works if OSM fails

Not included (still not-integrated):

- Route calculation, hike distance/time, elevation gain/profiles
- Activation-zone polygons
- Public/private land, gated-road certainty
- Weather, daylight, propagation, spots, alerts, logging
- Offline maps, GPX, multi-summit trips, ranking, billing
- AllTrails / Gaia / onX scraping

## Architecture

```
Selected summit
        ↓
SignalTerrainSotaAccess  (ss-access-provider.js)
        ↓
Overpass live  or  labeled OSM fixture
        ↓
SignalTerrainSotaAccessModel  (ss-access-model.js)
        ↓
Map layers + Summit Detail Access
```

The map UI does not contain Overpass query strings. Planning (`ss-planning-provider.js`) consumes a normalized access catalog and keeps hike-route fields not-integrated.

## Query strategy

| Item | Value |
|------|--------|
| Source | OpenStreetMap via Overpass API |
| Host | `https://overpass-api.de/api/interpreter` |
| Method | GET `?data=` encoded QL (also acceptable as POST) |
| Radius | **5000 m** from the selected summit |
| Features | `highway=path\|footway\|track` ways; `highway=trailhead` nodes; `amenity=parking` nodes/ways; `route=hiking` relations (**tags only**, no assembled route geometry) |
| Timeout | 15 s client abort; `[timeout:25]` in QL |
| Default runtime | Labeled fixture for **W2/GC-001** (Slide Mountain) |
| Optional live | `?access=live=1` — live Overpass, then Slide fixture fallback on failure |

**Why 5000 m:** Catskills high-peak parking is often 3–5 km from the summit. Slide Mountain Parking Area is about 3.4 km west of `W2/GC-001`. A 2.5 km radius would miss it. 5 km is still a bounded selected-summit query, not a region dump. `DEFAULT_RADIUS_M` is the single tuning constant.

Do not query the entire W2/GC region on startup. Access loads only after summit selection.

Hiking **relations** such as the Long Path can contain hundreds of members. V0.2 lists their names as nearby mapped routes and draws **individual ways** already in the radius. It does not stitch members into a fake through-route.

## Normalized access model

Each feature keeps:

- `kind` — `trail` · `trailhead` · `parking` · `named-route`
- `source` — `openstreetmap`
- `osmType` / `osmId` / `provenanceUrl`
- `name` — OSM `name` or **null** (never invented)
- relevant tags (highway, surface, access, parking, fee, …)
- `geometry` for ways (simplified, not joined across ways)
- `lat` / `lng` (centroid or midpoint)
- `distanceKm` / `distanceLabel` for trailheads and parking (`"{n} km straight-line"`)

Trailheads: `highway=trailhead`, or parking whose OSM name contains “trailhead” (e.g. Giant Ledge Trailhead mapped as `amenity=parking`).

Catalog `status`:

| Status | Meaning |
|--------|---------|
| `pending` | Lookup in flight |
| `ok` | Retrieval succeeded and at least one feature exists |
| `empty` | Retrieval succeeded; nothing matched in the radius |
| `unavailable` | Request failed, malformed, or no fixture/live for this summit |

Empty is not “no trail exists.” Unavailable is not empty.

## Caching

- In-memory per page session, keyed `signalterrain-sota-access-v0:{summitId}:{radiusM}`
- `sessionStorage` copy of the fixture/live payload for the same key (tab lifetime)
- Re-selecting the same summit does not re-hit Overpass
- Age is the catalog `retrievedAt`; V0.2 does not keep a durable localStorage archive
- Clear via `SignalTerrainSotaAccess.clearCache()` (tests)

---

## Provenance and ODbL

- Map attribution includes OpenStreetMap contributors
- Footer cites OSM copyright / ODbL
- Detail rows show `OSM way/node/relation/{id}`
- Internal objects keep `provenanceUrl`

**Current interpretation (not legal advice):** displaying OSM-derived geometries and tags with attribution is normal database-contents use. A share-alike obligation can apply if Waypoint publishes a **derivative database** (for example a redistributed combined access extract). V0.2 ships a labeled development fixture of retrieved OSM records for CI/offline; it is not a commercial data product. Do not strip attribution. Resolve broader ODbL publication questions before any public launch of downloaded extracts.

---

## Failure behavior

OSM access is an enhancement. Failure must not block:

- map startup, summit markers, search, detail, nearby summits, geolocation

Show a calm “OpenStreetMap data unavailable” (or the fixture-miss reason) in Access. SOTA facts stay on screen.

Other W2/GC summits without `?access=live=1` use the honest unavailable reason: no labeled fixture for that summit (not a fake empty OSM result).

## Visual

Existing charcoal alpine / brass / radio-cyan identity. Trails: subdued ridge-green polylines under summit markers. Parking: small brass **P**. Trailheads: ridge-green peak mark. Selected SOTA marker stays cyan-dominant. Layer chips toggle each overlay independently. After access data loads successfully, the map fits the summit plus mapped parking/trailheads (`maxZoom` 14), or zooms to 13 if those points are missing, so nearby paths are visible. That zoom is **not** a route highlight.
