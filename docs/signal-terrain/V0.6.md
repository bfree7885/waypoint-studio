# SignalTerrain V0.6

**Status:** In development · unpublished · `noindex`  
**App route:** `/apps/summit-signal/` (do not occupy `/apps/signalterrain/`)  
**This release:** Route to Activation Zone

> **SignalTerrain (SOTA/outdoor, unpublished) is a new product definition and is not the retired SignalTerrain Cyber product.**

> **SignalTerrain remains unpublished.** It is not in public navigation, the homepage, About/Support, or the sitemap. `noindex` and `robots.txt` Disallow stay in force.

> **Route to Activation Zone identifies a legitimate routed entry into the calculated Activation Zone. It does not identify a globally optimal or recommended operating location.**

> **Geographic presence inside the mapped zone is not a valid SOTA activation.** Radio contacts and other SOTA rules remain the operator’s responsibility.

V0.1–V0.5 remain in force: summit map, OSM access, user-selected Route to Summit, 25 m terrain-derived Activation Zone, Slide Mountain acceptance, Hunter Mountain AZ fixture. V0.6 adds an explicit second routing destination. It does not change the 25 m closed-contour rule, Slide AZ cell counts, Hunter AZ cell counts, or Route-to-Summit geometry.

---

## Goal

Answer, from a selected mapped access point:

**How do I hike to the calculated Activation Zone without necessarily routing all the way to the exact summit coordinate?**

The destination is terrain- and network-grounded. SignalTerrain does not invent an activation point, polygon centroid, nearest vertex, 25 m contour coordinate, or straight-line hop.

---

## Route to Summit vs Route to Activation Zone

The operator chooses destination mode deliberately:

| Mode | Destination | Geometry |
| --- | --- | --- |
| **Route to Summit** (V0.3, default) | SOTA summit coordinate (summit vicinity) | Full Valhalla pedestrian route |
| **Route to Activation Zone** (V0.6) | First valid routed AZ entry on that same Valhalla geometry | Prefix of the Valhalla polyline through the interpolated AZ crossing |

UI: **Route to: [ Summit ] [ Activation Zone ]** in Plan the Hike. Switching mode does not pick a new trailhead. Changing parking/trailhead recomputes the current mode without a page reload.

Route to Summit is never silently replaced. If Route to AZ fails, the summit route, Activation Zone, and prior planning information stay.

## Candidate-generation method

**Name:** `valhalla-summit-route-az-intersection`  
**Algorithm version:** `signalterrain-sota-az-route-v0`

Pipeline (not UI code):

1. Load the existing V0.3 Valhalla pedestrian route from the selected access point to the summit coordinate (labeled fixture in CI; live Valhalla remains `?route=live=1`).
2. Relate that provider geometry to the calculated AZ (`relateRoute`).
3. Emit candidates that lie on that Valhalla geometry:
   - **`first-az-entry`** — first outside→inside crossing (interpolated on the Valhalla segment).
   - **`route-terminus-inside-az`** — Valhalla destination if that point is inside/on the AZ (the summit-route terminus). Deduped if it is the same point as the first entry.
4. For each candidate, clip the Valhalla polyline to a prefix that ends at the candidate. That prefix is the candidate route. No new path is invented.
5. Validate. Select. Return a normalized Route-to-AZ result.

OSM trail fragments that intersect the AZ but are **not** on this Valhalla polyline are **not** treated as routable destinations in V0.6. Independently routing extra Valhalla destinations is out of scope (see V0.7).

This is not a dense brute-force sample of the AZ boundary. Typical candidate count attempted is **2** when the summit route enters the AZ (first entry + terminus).

## Route validation

A candidate is valid only if all of the following hold:

- the parent route is a Valhalla pedestrian result (`status === "ok"`, geometry ≥ 2 points)
- the candidate is not a straight-line / synthetic hop
- the prefix terminal point is inside or on the calculated AZ
- `relateRoute` reports that the prefix geometry actually enters the AZ
- distance is along-route haversine of the Valhalla prefix, not a geodesic shortcut

Invalid routes are rejected. There is no fallback to a straight line, nearest polygon vertex, centroid, or a summit route relabeled as an AZ route.

---

## Candidate-selection criterion

**Criterion id:** `shortest-routed-az-entry`  
**UI label:** Shortest routed AZ entry found

Among valid candidates, choose the shortest routed distance from the selected access point. Equal-distance tie-break: lower latitude, then lower longitude (deterministic).

The selected coordinate is a route-planning result for this access point, this AZ version, and this candidate method — not a global recommendation.

## Normalized model

`SignalTerrainSotaAzRouteModel` owns the result. Minimum fields:

- summit reference and coordinate
- selected access point
- destination mode (`activation-zone`)
- AZ geometry/version identity (`azCalculationVersion`, `azCellCount`, `azThresholdM`)
- candidate-generation method
- selected candidate coordinate / AZ entry
- route provider (`valhalla`) and profile (`pedestrian`)
- route geometry (Valhalla prefix)
- route distance and label
- estimated duration when legitimate
- candidate counts attempted / valid
- selection criterion and label
- calculated timestamp
- provider attribution
- status / error information
- `straightLineUsed: false`

Provider-specific Valhalla trip objects stay in route fixtures, not in UI code.

---

## Caching / versioning

Cache identity (`ss-az-route-provider.js` / `cacheKey`) includes:

- access OSM id
- summit id
- routing profile (`pedestrian`)
- route provider (`valhalla`)
- AZ algorithm version + cell count + threshold
- candidate-generation method version
- selection criterion

Summit-route cache keys are unchanged (`signalterrain-sota-route-v0:…`) and do **not** include destination mode, so an AZ prefix never overwrites the V0.3 summit route. AZ-route cache keys are a distinct `signalterrain-sota-az-route-v0:…` namespace. Stale results are not reused after AZ algorithm/version or cell-count changes.

## Elevation handling

Use the existing V0.3 USGS 3DEP pipeline. For a successful Route-to-AZ result:

1. Load the labeled (or live) 3DEP samples for that access route.
2. `TerrainModel.clipProfile(elev, azDistanceKm)` keeps samples at or before the prefix distance.
3. Re-run the 5-point moving average and cumulative gain/loss on those samples.

This is not “scale the summit-route gain by distance fraction.” It is a recomputation on the prefix samples of the same Valhalla geometry. If too few samples remain, elevation is unavailable and the AZ route is still shown.

---

## Time estimate

Same V0.3 methodology. Valhalla’s duration is for the full summit route. The AZ prefix duration is:

`durationSec * (azKm / summitKm)`

labeled **estimated** (`durationSource`: `valhalla-pedestrian-distance-fraction`, display still `~` rounded to 5 minutes). If the prefix is effectively the full summit route, the original Valhalla duration is used. No new pace model.

---

## Failure states

Distinguished statuses:

| Status | Meaning |
| --- | --- |
| `ok` | Route to AZ found |
| `az-unavailable` | AZ unavailable |
| `no-candidate` | No valid AZ routing candidate found |
| `unavailable` / `timeout` | Routing service unavailable |
| `no-route` | Route provider returned no route |
| `all-candidates-failed` | All candidate routes failed validation |
| `generation-failed` | Candidate generation failed |
| elevation `unavailable` after `ok` | Terrain/elevation unavailable; AZ route kept |

No straight-line, summit-route relabel, or nearest-polygon fallback.

## Known limitations

- V0.6 evaluates AZ-entry candidates **on the selected-access Valhalla summit route only**. Other mapped trails that intersect the AZ are not independently routed. The selected entry is the shortest among those candidates, not a globally optimal approach from every trail.
- Candidate count is typically two (first entry + terminus). That is documented, not hidden.
- AZ prefix duration is a distance fraction of Valhalla’s summit-route time, not a second Valhalla request.
- 3DEP samples follow the full-route simplify/sample pattern; prefix gain is recomputed from those samples clipped by distance, which may include nearly all samples when the remaining summit spur is short (Hunter).
- FOSSGIS Valhalla remains development-only. CI uses labeled fixtures and must not call live SOTA, 3DEP, Valhalla, or Overpass.
- Only Slide and Hunter have access/route/AZ fixtures. Other W2 summits stay honestly unavailable unless live is requested.
- SignalTerrain is **unpublished**. No billing, public navigation, or SEO exposure.
